# 待办：文本顺序即注意力

这份文档记一条贯穿待办、笔记、记忆三处的原则，以及由它推出的几个决定。模型字段与行为以 `plugins/host/omd-todo/README.md` 为准；这里只写“为什么这样排”。

## 原则

待办、上下文笔记这类东西，虽然有 list/set 的语义，但**最终都是以一段文本注入上下文的**。文本单向生长，位置决定可读性：

- 靠近当前请求的一端最容易被读到；
- 越往另一端，越容易沉没——不是因为内容不重要，而是因为它离注意力远。

所以顺序不是展示偏好，是注意力预算的分配。任何“排序”功能都必须先回答：哪一端是可读端。

## 由原则推出的决定

1. **rerank 是重排新老条目，不是排优先级**。它把还活着、要推进的条目往可读端移动，把陈旧、搁置、已完成的往另一端推或移出。一个标了高优但三天没动的条目，不该压在刚更新过的条目前面。
2. **顺序必须写回树**。看板、`dsh-resource://todo/<sessionId>` 的渲染、判官上下文都按树的顺序读；三处各自排序必然漂。
3. **结构与语义分开**：老化淘汰（多久没动、已完成留存多久）用确定性规则；语义判断（哪些其实是同一件事、哪些已经过时）才用判官，且默认关。
4. **completed 不占可读预算**：完成项要么推到不可读端，要么归档；留在活跃区只会挤掉真正要推进的条目。
5. **可读端 = 前**（2026-10-22 核对）。待办目前没有任何常驻注入：`omd-todo` 只注册工具、`todos` 投影与 `dsh-resource://todo` 路径源，上游 `tool-todo` 也只注册投影。模型看到待办只有两条路——`todo_write` 的返回回显（树序，含 state 不含 goal），和按需读路径（计数行在最前，正文按树序）。另外两个读者是看板与判官上下文，后者超 30 条**截尾**。四处都从头读、唯一的预算读者裁的是尾巴，所以排前面 = 更容易被读到。

   这条是待验证假设，不是定律：依据是阅读顺序与截断方向，不是与请求的 token 距离。若今后改为常驻注入（system prompt 分节或 pre-step 消息），整块仍在当前请求之前一次读完，结论不变；但若注入块变长、模型倾向回读尾部，这条翻转。判定办法是观测“实际先动的那条在排序里的位置”，不为此加开关。

## 三态模型

`state: 'active' | 'inactive' | 'completed'`——单一轴，取代原先 `status`（pending/in_progress/completed）加布尔 `active` 的组合，因为那个组合空间里大半状态没有意义。

上游 `todo/write` 只认三态字符串，映射为：`active → in_progress`、`inactive → pending`、`completed → completed`。**上游那条 `at most one in_progress` 校验碰不到我们**：`omd-todo` 自己 `session.append('todo/write', …)`（`plugins/host/omd-todo/src/service.ts:160`），不走上游 `todo_write` 工具；而那条工具本来就在 `omd-tools-policy` 的拒绝名单里。所以并行与否只看我们自己的配置 `allowParallelActive`，profile 里定为 `true`（并行子任务是常态，单活跃纪律会逼模型把正在并行推进的条目写成 `inactive`）。
