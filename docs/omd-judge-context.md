# 判官上下文配方

判官（judge）在我们这里有多处消费者：待办驱动的“要不要催”、可视化委派的“要不要画”。它们共用同一套输入组装规则——**不要各自拼一份**，两份一定会漂。

## 为什么不能直接喂整个会话

判官的判断依赖的是“现在发生了什么”，不是完整历史。整段丢进去有三个问题：信号被稀释（最近的意图淹没在早先的工具输出里）、成本随会话长度线性增长、而且判官会开始对与本次判断无关的细节发表意见。

## 组装顺序（预算用完就停）

| 优先级 | 内容 | 说明 |
|---|---|---|
| 1 | 任务说明 | 常量，放 system 里。同一会话反复调用时这段命中缓存 |
| 2 | 待办状态 | active 且未完成的条目：`status`、`goal`、`explanation` 摘要；保留树形，超过 30 条截断并注明 |
| 3 | 用户最后一条消息 | 原文，超长截断到约 800 字 |
| 4 | 助手最近 3 条消息 | 每条约 600 字，按时间顺序 |
| 5 | 历史调用记录 | 剩余预算全给这里：**未完成/异常的调用优先**（有 call 无 result、`isError`、被中断的，标 `unfinished`）；然后是最近的正常调用（name + 参数摘要 + 结果首行）；填不下就停，末尾写“更早的 N 条已省略” |

**不放进去**：系统提示、工具 schema、spill 全文、图片内容。这些既稀释信号又烧钱。

## 预算与降级

默认 4000 token，可配。超预算时砍的次序是第 5 段 → 第 4 段 → 第 3 段；任务说明与待办状态最后砍——它们是判断的骨架。

## 输出

严格 JSON：`{ decision, reason, confidence }`。

- 待办驱动：`continue | wait | done`，`confidence` 低于门槛（默认 0.75）按 `wait`。
- 可视化：`visual | none`，同样有门槛。
- 解析失败、判官不可用 → 一律按“不做”处理（`wait` / `none`）。**默认不动**是这条链上唯一安全的默认值。

## 共享方式

组装逻辑做成共享函数（输入 `{ session, budget, purpose }`，输出消息数组），两个消费者各自只提供自己的任务说明与输出 schema。谁先落地谁导出形状，另一边改成消费它，不允许各写一份。
